# ADR-080: Trusted SCORM 2004 activity delivery and durable sequencing

Epic #133 S6 extends S5 on an owned successor. Both content and server reuse the pinned scorm-again sequencing engine. Only the server's result grants activity delivery or official completion. A client checkpoint can contain CMI and a navigation request, never a sequencing tree/snapshot/rollup summary.

The namespace-aware manifest parser compiles an explicit profile into engine activity settings: nested SCO leaves/folders, flow/choice/choiceExit/forwardOnly, constrained choice, known pre/exit/post conditions, primary/local objectives, registration-local objective maps, all/any/count/percent rollup rules, delivery controls and attempt limits. Unknown elements/attributes, references and unsupported edition semantics fail before launch. System-global maps are refused rather than silently reinterpreted as registration-local. Sequencing collections, retry/retryAll rules, duration limits, randomization/selection, ADL presentation/rollup extensions, weighted completion, asset activities and fourth-edition shared data remain explicit unsupported profiles requiring further conformance work. This is a tested support profile, not complete SCORM certification.

Each overall attempt owns an envelope with exact attempt/package SHA-256/edition/engine identity and a bounded 1 MiB synchronous engine snapshot. SQLite saves it in the same transaction as accepted per-SCO CMI, time deltas, revision, receipt, audit and official proof. Constructor recovery loads only a trusted database snapshot. The pinned upstream current-activity restore setter reactivates the activity path; the adapter restores persisted active flags afterward so ended/suspended sessions cannot bypass new-attempt limits.

Commit validates and stores pending navigation without executing it. Terminate replays through the trusted engine, checks navigation on a restored copy and records the resulting delivery/rollup. Capture the finishing SCO's normalized CMI before upstream replaces protected launch fields for the next SCO. Learner content can report its own data; this is not anti-cheat evidence. Choice/direct launch is also checked by the engine. Replacing a launch closes its predecessor capability, preserving a single writer.

The authenticated Pear shell reconciles the exact launch/sequence after ACK and launches the server-selected next SCO under the existing tracking consent. A raw content message cannot choose the delivery target. Lost ACK replays the same immutable request; navigation/time cannot run twice. SuspendAll and interrupted server/browser sessions recover the prior SCO and objective map. Technical SCO attempts have separate counters, empty state on a new attempt, historical rows and immutable launch binding (migration 047). They do not create course/item retakes or rewrite the official ledger.

Official projection requires every required SCO's durable finished/status/score evidence and the engine root's completed/passed rollup under the published policy. The proof records a minimal root rollup alongside package/attempt/engine provenance. Existing quiz, nested award/cycle, live audience, preview/practice, retirement/revocation and fresh-enrollment rules remain authoritative.

Validation covers all three editions, objective-known/unknown gating, low score and direct choice denial, Commit vs Terminate, all-child rollup, lost-ACK replay, suspend/resume, SQLite/server reopen, forged snapshots, wrong snapshot identity, audit rollback, stale/two-tab writers and technical attempt limits. Built Chromium journeys validate authenticated automatic next-SCO delivery after lost ACK.

Primary reference: [ADL SCORM 2004 4th Edition Sequencing and Navigation v1.1](https://lms.technology/for/scorm/2004/4th_edition/standards/SCORM_2004_4ED_v1_1_SN_20090814.pdf), CAM/RTE references in ADR-079 and the pinned engine's public source/types. Production and native execution remain disabled pending their platform gates.
